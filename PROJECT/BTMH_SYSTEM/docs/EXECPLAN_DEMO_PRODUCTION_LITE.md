## Current architecture and observed failures

Audit source: `docs/DEMO_PRODUCTION_LITE_AUDIT_20261008.md`. One global StaticCameraService/WALKBY runs real recognition. Auxiliary fleet readers only provide JPEG and expire with browser leases. Native media serves the active camera and existing scoped fallback paths. Recognition metadata currently comes from the global camera. Store and camera assignment tables exist, but are not connected to camera CRUD/event attribution. Events contain mutable camera_source labels. Attendance has shift assignments and presence sessions, but reports ignore assignment effective dates and can label absence before shift end. Visitor observation sessions are not entrance visits. History filters operate on a truncated browser feed.

## Protected areas and non-goals

No changes to FaceID models/recognition thresholds, PAD thresholds/security decisions, anti-spoof policy, SMS, launcher, recorder internals or fundamental camera handover/registry safety. No rewrite of MediaMTX/WebRTC. Reuse existing camera IDs, stores and zone_name; do not introduce a competing zone/store model. No destructive schema changes, backfilling events from mutable current mappings, hard-coded shop/camera names or secrets. No inference that last_seen minus first_seen equals working hours. No advanced anonymous cross-camera re-identification or unique-person metric. No installer/deployment work.

## Migration and rollback strategy

Add nullable event attribution columns (camera_id/store_id/zone text and name snapshots) and needed camera AI/counting settings with safe disabled defaults. Retain old columns/API signatures. Existing camera assignment table remains canonical; enforce one current store per camera at the write boundary. Legacy event attribution remains unknown unless already recorded evidence proves it. Effective-dated shift history is additive; seed only the existing assignment's actual known effective interval. Visitor entrance visits are separate from legacy observation sessions, because the measures differ. Migrations are idempotent and use the existing SQLite/PostgreSQL compatibility connection. No DROP/rename or automatic rollback. Source checkpoint backup is optional and must exclude database, credentials and runtime data. Deploy schema only through the application migration path, not against a customer database during development.
